# 流程规则（P）

开工、提问、交付、合并、评审。卡片格式见 [索引](00-索引.md)。

## P-01 开工条件

规则：从 GitHub 当前 Milestone 取带 `status/ready`、前置已合并的结果型 Issue（前置写在 Issue 的“开工”一节）→ 建分支 `feat|fix/<Issue 号>-<短名>` → 先写失败的测试，再写实现。
理由：每项工作可追溯到一个结果；先有失败的测试才知道做对了。
状态：生效
检查：评审

## P-02 Issue 与未决问题

规则：Issue 用模板“结果”新建，默认带 `status/needs-decision`：先把需要人决定的事写进“未决问题”，人在 Issue 里答复、答复写进[决策记录](../decisions/README.md)后，改为 `status/ready` 再开工。卡在未决问题上时，转去做其他已就绪的 Issue，不自己拍板。
理由：需要人决定的事不能由 AI 默默选定。
状态：生效
检查：评审

## P-03 进度写在 Issue 描述里

规则：进度、决定、实施记录更新在 Issue 描述里，不靠评论；ROADMAP.md 不写进度。
理由：描述是唯一的事实来源，新会话只读描述就能接上。
状态：生效
检查：评审

## P-04 先停下来问人

规则：以下事项由人决定。能在开工前看出来的，写进 Issue 的“未决问题”；开工后才发现的，在 PR 里提出，等答复再继续：
- 改变 README 指标的目标值或口径，或接受某项指标不达标（如 D-027、D-030）。
- 权限语义：检索过滤、角色与权限点、超级管理员、会话失效。
- 新增 Maven 模块、外部服务、依赖或抽象层。
- 删除或放宽测试、断言、评测题（尤其是越权题）、架构规则。
- 数据库的不兼容变更；客户数据、密钥的处理方式。

理由：这些事影响产品口径、安全或长期维护成本。
状态：生效
检查：评审

## P-05 交付：一个 Issue 一个 PR

规则：开 PR，按模板写清改了什么、验收标准逐条的证据、评测指标变化、风险与未完成项。一个 Issue 对应一个 PR；一个 PR 做完一件完整的事，不为控制行数拆分。不写单独的证据文件。
理由：评审的单位是一项完整、可验证的能力。
状态：生效
检查：评审

## P-06 只为路线图上的结果开 Issue

规则：写明验收标准。工作中发现的问题属于当前结果的，在当前 PR 里修（包括决策记录、文档、测试）；不属于的，记进 ROADMAP.md 的待办，排期时合并成结果型 Issue。
理由：避免零散 Issue 和顺手改动。
状态：生效
检查：评审

## P-07 质量类与界面类 Issue

规则：质量类 Issue 以指标为验收标准，一个 PR 里可以多轮“改动 → 评测”，每轮数据写进 PR 描述。界面类 Issue 先交 MSW 原型给人确认，确认后在同一个 Issue 里接接口。
理由：质量看指标；界面先确认再接接口，避免返工。
状态：生效
检查：评审

## P-08 main 变红时的例外

规则：唯一的例外：main 变红时可以直接开小的 `fix` PR，不单开 Issue。
理由：先恢复 main 的可靠性。
状态：生效
检查：评审

## P-09 完成定义

规则：验收标准逐条打勾，每条在 PR 描述里有证据（测试名、eval 运行链接和指标、或手工步骤结果）。有一条没达到，PR 写 `Refs #n`，Issue 不关闭；经人同意后，缺口拆成新的结果型 Issue（写明理由）再关闭。缺口不能只写在“风险与未完成项”里。
理由：没有证据的完成不算完成。
状态：生效
检查：评审

## P-10 文档同步

规则：行为、配置、指标口径变化时，README / AGENTS.md / ROADMAP.md / 决策记录在同一个 PR 里更新；每条规则只在一处写正文，其他地方链接过去。
理由：文档写的是当前结论，避免多处正文互相矛盾。
状态：生效
检查：自动[DocLinksTest]（只检查链接、卡号和决策编号有效；内容是否同步靠评审）

## P-11 合并

规则：从 main 建分支，不以另一个未合并的分支为 base；上一个 PR 合并后再开下一个（squash 合并后，叠放的上层 PR 必然冲突）。CI 的 `backend`、`frontend`、`image` 全绿才能合并（分支保护），涉及检索或生成时 `eval` 的结果写进 PR。改 `ci.yml` 的任务名时同步改分支保护。CI 失败、合并冲突、评审意见由开 PR 的一方（含 AI）自己修并推送，不等提醒。推送后核对远端提交号。人读过 PR 后开启 auto-merge，CI 全绿由 GitHub 合并；AI 不自己合并。
理由：叠放 PR 必然冲突；合并前要有可靠的 CI 结果。
状态：生效
检查：评审

## P-12 评审清单

规则：自动检查已覆盖的（模块边界、架构规则、迁移命名）不必再看。

| 方面 | 看什么 |
| --- | --- |
| 权限与越权 | 检索过滤是否仍只在一处；新接口有没有登录和角色注解；越权场景是否有测试和评测题 |
| 范围 | 是否对应一个 `status/ready` 的 Issue，验收标准是否真的验证了；有没有顺带做没要求的事 |
| 设计 | 业务规则归哪个聚合或服务；有没有只转发的层；是否触及“先停下来问人”的事项 |
| 正确性 | 边界输入、并发、事务范围、模型调用失败和超时时的行为 |
| 可读性 | 方法只做一件事，超过约 30 条语句或分支嵌套过深就拆（参考 `AnswerService` 的编排加步骤） |
| 测试与评测 | 正常和关键失败路径都有测试；断言的是结果；评测数据是否支持结论（看多轮，不看单次） |
| 文档 | 决定已写进决策记录；文档写的是当前结论 |

理由：把机器查不了的方面列出来，评审不重复机器的工作。
状态：生效
检查：评审

## P-13 语言

规则：提交信息、注释、文档用简体中文；代码标识保留英文。提交信息前缀用 `feat`、`fix`、`build`、`docs`。
理由：团队语言统一。
状态：生效
检查：自动[check_pr_guard]（只检查 PR 标题前缀；其余靠评审）
