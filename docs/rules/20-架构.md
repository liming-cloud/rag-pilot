# 架构规则（A）

设计原则、模块与依赖、目录结构。卡片格式见 [索引](00-索引.md)。

## A-01 通用内核 + 行业包

规则：内核不写死行业内容，提示词角色、话术、文案、推荐问题、行业词表放在行业包（`rag-settings/src/main/resources/industry-packs/<名字>/pack.yml`），评测集按行业包分目录（D-045）。
理由：同一内核服务不同行业。
状态：生效
检查：自动[KernelNeutralityTest]

## A-02 权限由系统判定

规则：权限由系统判定，不交给模型；功能权限（RBAC，细到按钮）和资源权限（知识库授权）分开，管理员也不绕过资源授权。
理由：模型的判断不可审计，权限必须确定。
状态：生效
检查：测试（`RbacTests`、`KnowledgeAccessTests`）

## A-03 可追溯与人确认

规则：每个结论都能追溯；依据不足时明说。预测交给专门的模型；写操作先经人确认。
理由：可信运营助手的底线。
状态：生效
检查：评审

## A-04 能评测才算完成

规则：改动以多轮评测结果为准。
理由：质量用数据说话，单次结果有波动。
状态：生效
检查：评审

## A-05 权限过滤只在一处

规则：权限过滤只在 rag-knowledge 的检索服务里写一处，禁止绕过。
理由：多处过滤必然漏改，越权风险最大。
状态：生效
检查：自动[ArchitectureRulesTest]（`SEARCH_FILTER_IN_ONE_PLACE`）

## A-06 松耦合：外部能力只在 infrastructure 用

规则：组件或上下文对外提供能力，上下文只在自己的 `infrastructure` 层调用外部能力，实现 `application` 声明的端口（参数、返回值、异常都用本上下文的类型）；`application`、`domain` 只关注业务，不知道外部能力怎么实现。只有一个上下文用的库放在它的 `infrastructure`（如 PDFBox、POI、Sa-Token 的会话和密码摘要），多个上下文要用的做成平台层的能力模块（如 rag-ai、rag-persistence、rag-cache），同样只在 `infrastructure` 里引用。Spring 是基础框架，不隔离；web 层的 Sa-Token 注解例外。上下文的 `api`、`web`、`application`、`domain` 只能依赖 JDK、Spring、JSpecify、SLF4J、rag-shared、本上下文和其他上下文的 `api`，以后新增组件不用补规则。
理由：D-054；换实现不影响业务代码。
状态：生效
检查：自动[ArchitectureRulesTest]（`CONTEXT_LAYERS_ONLY_USE_ALLOWED_DEPENDENCIES`）

## A-07 AI 能力只经 rag-ai

规则：AI 能力只经平台层的 rag-ai（Spring AI 防腐层，D-052）：按能力提供文字生成（一次性、流式）、问题改写、向量化、重排、连通测试，参数和返回值都是自己的类型，内部用足 Spring AI 并打开它自带的观测；提示词和判断规则是上下文的策略，不放进 rag-ai；上下文只在 `infrastructure/ai` 里经自己按用途声明的端口调用它（D-054）。上下文层用 Enforcer 禁止依赖 Spring AI，`ArchitectureRulesTest` 检查代码。各用途用哪个服务商和模型由 rag-settings 经 `ModelRouting` 提供（D-043、D-044）。服务商密钥用 AES-GCM 加密存库，主密钥只从环境变量 `RAG_MASTER_KEY` 读；环境变量里的密钥同样只从环境变量读；接口、日志都不返回密钥明文，界面只显示后 4 位。
理由：框架可替换，密钥不泄露。
状态：生效
检查：自动[ArchitectureRulesTest]（`SPRING_AI_ONLY_IN_RAG_AI`；密钥不返回明文靠 `ModelSettingsTests`）

## A-08 DDD：聚合与上下文边界

规则：聚合只在 knowledge、answering；上下文模块之间只用对方的 `api` 包或监听事件，依赖方向见 A-10。
理由：保持聚合少而清晰，模块之间只经公开合同交互。
状态：生效
检查：自动[SharedKernelTest、ModularityTests]

## A-09 缓存只经 rag-cache

规则：缓存只经平台层的 rag-cache（D-053、D-054）：上下文在 `application` 声明业务化的缓存端口（如 `AccessSnapshotCache`），`infrastructure/cache` 用 `Caches`、`TypedCache`、`CacheSpec` 实现；用不用 Redis、一级还是二级、过期时间都在 rag-cache 的配置里，上下文不知道。Redis 客户端 Redisson 和一级缓存 Caffeine 只在 rag-cache 里（上下文层用 Enforcer 禁止依赖，`ArchitectureRulesTest` 检查代码）。缓存什么、何时清除由上下文决定：改了被缓存的数据，在同一个事务里调端口的清除方法，提交后才清；不缓存可访问的知识库、检索结果和答案。测试约定见 T-07。
理由：缓存实现可替换，清除时机由业务决定。
状态：生效
检查：自动[ArchitectureRulesTest]（`CACHE_CLIENTS_ONLY_IN_RAG_CACHE`、`CACHE_ONLY_IN_INFRASTRUCTURE`；清除时机靠 `CacheConsistencyTests`）

## A-10 上下文依赖方向

规则：identity 不依赖其他上下文；settings 依赖 identity；knowledge 依赖 identity、settings；data 依赖 identity；answering 依赖 identity、knowledge、settings、data（经 data 的 `api` 按数据范围查数据，D-062）；evaluation 不依赖其他上下文。平台层的 shared、ai、persistence、cache 都可以用（evaluation 经 ai 调评判模型），平台层不依赖上下文。各上下文在根包 `package-info.java` 的 `allowedDependencies` 里声明，`ModularityTests` 检查。上游要用到下游的东西时（如权限点清单），由上游在 `api` 里定义接口、下游实现，不反向依赖。
理由：依赖单向，避免循环。
状态：生效
检查：自动[ModularityTests]

## A-11 后端目录：三层聚合与上下文子包

规则：后端按类型分三层聚合（D-052）：`backend/platform`（平台层：rag-shared、rag-ai、rag-persistence、rag-cache）、`backend/contexts`（上下文层：五个上下文）、`backend/boot`（启动层：rag-app）。每个 Maven 模块 `rag-<名>` 对应根包 `com.liming.rag.<名>`。上下文模块（identity、knowledge、answering、evaluation、settings、data）根包只放 `package-info.java`，类只能在五个子包里：
- `api`：对其他模块公开的合同（接口、record、枚举、事件），不暴露模块内部类型；
- `web`：Controller、请求响应 record；
- `application`：用例服务，以及它需要的端口接口（如 `ChunkIndex`、`FileStorage`）；按用例分子包，子包之间不循环依赖：answering 的 `ask`、`conversation`、`review`、`insight`，identity 的 `account`、`role`、`auth`、`audit`，knowledge 的 `ingestion`、`search`、`knowledgebase`（含授权），settings 的 `model`、`system`、`pack`，data 的 `grant`、`scope`；多个子包共用的异常、`Properties`、端口和枚举留在 `application` 根下；
- `domain`：聚合、值对象、领域规则，只在 knowledge、answering；
- `infrastructure`：端口的实现，按技术分子包（`persistence`、`storage`、`parsing`、`security`、`cache`）。

理由：层次清晰，规则可自动检查。
状态：生效
检查：自动[PackageLayoutTest]

## A-12 内部类型是否提成顶层

规则：Service、聚合等类里的内部 record、枚举，按下面的标准决定是否提成顶层（放在使用它的 `application` 子包里，名字带业务含义，如 `ImportRow`、`GapReport`，不叫 `Row`、`Item`）：
- 提成顶层：被 web 展示、被别的包或多个文件引用的类型（返回值、读取结果、列表项），如 `DocumentRow`、`Rewrite`、`ProviderView`；
- 保持内部：只作外层方法参数或返回值、由调用方构造的类型（`Upload`、`NewTurn`、`AskRequest`）、聚合自己的状态枚举和异常、测试替身；
- 自动检查：web 不读取 application 里 `Service` 的内部类型（只 new 出来当参数的除外）。

理由：避免 web 依赖 Service 内部类型，又不把所有类型都拆出来。
状态：生效
检查：自动[ArchitectureRulesTest]（`WEB_NOT_USING_SERVICE_NESTED_TYPES`；提成标准靠评审）

## A-13 层间依赖方向

规则：`domain` 只依赖 JDK（含 JSpecify 空值注解）、rag-shared 和本模块的 `domain`、`api`；`application` 不依赖 `infrastructure`、`web`；`web` 不依赖 `infrastructure`、`domain`（展示用 application 的查询结果 record）；`api` 不依赖本模块其他子包。
理由：业务规则不依赖技术细节。
状态：生效
检查：自动[PackageLayoutTest]

## A-14 输入：web 只转交原始值

规则：web 只转交原始值（路径、查询参数和请求体里的字符串、数字），application 解析成枚举或值对象，不合规时抛本模块的业务异常；每个模块的解析写在一处。
理由：解析和校验是业务规则，不散在 web 层。
状态：生效
检查：评审

## A-15 租户

规则：单租户部署，`TenantId` 为以后多租户预留；哪些端口和设置不分租户见 D-051。
理由：为多租户留口子但不提前实现。
状态：生效
检查：评审

## A-16 共享内核 rag-shared

规则：只放多个上下文共同依赖、用纯 Java 表达、很少变动的东西——模型概念（租户和用户标识、错误分类 `ErrorKind` 与 `BusinessException`、聚合根标记 `AggregateRoot`）和通用工具（分页 `Paged`、空串处理 `Texts`、枚举解析 `Enums`，D-053）；只有一个上下文用的工具留在该上下文。只依赖 JDK（空值注解 JSpecify 除外），没有资源文件（迁移、配置归各自模块），不放业务规则；当前用户、权限码、各上下文自己的标识不放这里。新增类型前先在决策记录里写明理由（D-034、D-053）。
理由：共享内核改动等于改动所有模块的合同。
状态：生效
检查：自动[SharedKernelTest]

## A-17 平台层模块的包规范

规则：（D-064）
- rag-shared 扁平：对外只公开接口、record、枚举、异常和无实例的工具类（final、私有构造、只有静态成员，D-053）。
- 能力组件 rag-ai、rag-cache、rag-persistence：根包只放能力接口（含由上下文实现的接口，如 `ModelRouting`），类注释写清是什么能力、怎么用、失败抛什么；一种能力一个子包（名字用能力的名词，如 `generation`、`typed`），放该能力的契约类型（调用方必须直接用的 record、枚举、异常、句柄接口，类型上标 `@NamedInterface("<能力名>")` 导出）、实现、配置和单元测试，实现类包内私有；模块内多个能力共用的放 `common`（`ModelCallException`、`ModelUsage`、`ModelRoute` 这类调用方必须处理的标 `@NamedInterface("common")`，其余默认不对外）。根包接口要用到包内私有的实现时，经子包里的公开工厂（如 `InMemoryCaches`），工厂不导出。
- 公开要克制：只有根包接口、标了 `@NamedInterface` 的契约类型、模块内跨子包必须用的类型可以 public；不为测试而公开；能用 JDK 类型表达就不新增类型；新增导出类型时在 PR 里写“调用方为什么必须直接用它”。
- 能力子包之间不互相依赖（要共用就下沉到 `common`），`common` 不依赖能力子包。上下文在 `allowedDependencies` 里写到能力粒度（如 `"ai :: tool"`，根包写 `"ai"`）。
- rag-app 只放启动类和全局配置（含唯一的异常出口 `ApiExceptionHandler`）。

理由：平台层的公开面最小，能力之间互相独立。
状态：生效
检查：自动[PackageLayoutTest、ModularityTests]（“新增导出类型的理由”靠评审）

## A-18 聚合

规则：聚合根实现 `AggregateRoot`，只在 knowledge、answering 的 `domain` 包；`domain` 里的 `XxxRepository` 只为同包的聚合根 `Xxx` 而建。
理由：聚合边界清晰。
状态：生效
检查：自动[SharedKernelTest]

## A-19 错误

规则：业务失败抛本模块继承 `BusinessException` 的异常（错误码 `<模块>_<原因>`，说明是给用户看的中文，不含内部信息）；领域对象的规则违规（用户输入或操作能触发的）直接抛本模块 `domain` 包里继承 `BusinessException` 的异常（如 `AnsweringRuleException`），错误码与 application 的同一套，application 不再 `catch` 翻译；`domain` 不抛 `IllegalArgumentException`。`IllegalStateException` 只表示编程错误：调用方已先检查、正常流程走不到的前置条件（状态机守卫、重复赋 id 等），出现即按 500 处理（D-067）。模块不写 `@RestControllerAdvice`，统一由 `ApiExceptionHandler` 转成带 `code` 的问题详情。
理由：错误出口唯一，前端按错误码处理。
状态：生效
检查：自动[ArchitectureRulesTest]（`ONE_EXCEPTION_HANDLER`、`DOMAIN_RULES_CARRY_ERROR_CODES`；`IllegalStateException` 是否真是编程错误、错误码取值靠评审和 `ApiExceptionHandlerTest`）

## A-20 资源与测试的位置

规则：Flyway 迁移在 `db/migration/<模块名>/`，Mapper XML 在 `mapper/<模块名>/`。单元测试与被测类同包；跨模块的集成测试放在 rag-app。
理由：位置固定，便于自动检查和查找。
状态：生效
检查：自动[MigrationLayoutTest、MapperXmlLayoutTest]

## A-21 不随意新增模块、依赖和抽象层

规则：不新增 Maven 模块、外部服务、依赖或抽象层，除非[决策记录](../decisions/README.md)已记录理由。
理由：每个新增都是长期维护成本，由人决定（见 P-04）。
状态：生效
检查：评审

## A-22 客户数据和密钥不进仓库

规则：客户数据、密钥、截图不进仓库（本仓库当前为公开仓库）。
理由：仓库公开。
状态：生效
检查：评审

## A-23 规则误判或漏判时修规则

规则：能明确判定的约束由 `ArchitectureRulesTest`、`PackageLayoutTest`、`MigrationLayoutTest`、`MapperXmlLayoutTest`、`ModularityTests` 和前端的 `src/app/structure.test.ts` 自动检查。规则误判或漏判时，修改规则并补违规样例（`archfixture` 包），不绕过、不加例外。
理由：规则要靠样例证明有效，例外会让规则失去意义。
状态：生效
检查：评审
