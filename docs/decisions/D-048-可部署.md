# D-048 可部署：离线包、4 位版本号、停服务备份、用备份回退、部署验证进 CI（2026-11-02）

#129 经人答复：

- **离线包，不用镜像仓库**：打 4 位版本号的 tag（`v1.0.0.1`）时，CI 构建 app、web 镜像，连同 `compose.yml` 里按摘要锁定的 ParadeDB 镜像（重新打成 `rag-pilot-db:<版本>`，因为 `docker load` 之后摘要引用不可用）一起 `docker save`，和部署目录（Compose、脚本、运维手册、`.env.example`、写着版本号的 `release.env`）一起附在 GitHub Release 上。镜像分成三个文件，因为 Release 单个附件不能超过 2 GB。不新增外部服务；客户服务器能不能上网都一样。仓库里的 `deploy/` 仍可从源码构建，供开发用。
- **版本号**：4 位，主.次.修订.构建号；前三位按语义化版本（不兼容的数据库变更升主版本），构建号是同一版本重新打包时自增。由 tag 决定，构建时写进镜像的环境变量 `RAG_VERSION`，`/actuator/info` 和管理端左下角显示。升级演练用 `0.9.0.1` → `1.0.0.1`。
- **每个版本一个部署目录**：离线包解压成 `rag-pilot-<版本>/`，Compose 项目名固定为 `rag-pilot`，所以不同版本的目录操作的是同一套数据卷。升级在新版本目录里做，回退在旧版本目录里做；备份默认放在部署目录旁边的 `backups/`（`RAG_BACKUP_DIR`），换版本不受影响。
- **停服务备份**：`backup.sh` 停 app → `pg_dump` 自定义格式 → 打包上传文件卷 → 记下版本号和校验和 → 启动 app，数据库和文件完全一致，代价是每次停几分钟。期间 Nginx 对 `/api` 返回“系统维护中”（问题详情，页面直接显示）；为此 Nginx 改为每次请求经 Docker 内置 DNS 解析 app，app 重启后地址变了也能转发，app 没起来时 Nginx 也能先启动。备份不包含 `.env` 和主密钥。
- **恢复**：`restore.sh` 校验文件 → 要求备份的版本与部署目录的版本一致 → 停 app → 删库重建、`pg_restore` → 清空并解开上传文件 → 启动。BM25 索引随恢复重建。
- **升级与回退**：`upgrade.sh` 检查镜像和备份目录的剩余空间 → 停服务备份 → 用新版本启动（Flyway 自动迁移）→ 等健康检查 5 分钟 → 运行 `verify.sh`。迁移不可逆，不写反向迁移：回退 = 在旧版本目录里用升级前的备份恢复，升级后写入的数据会丢。启动超时（多是迁移失败）时停掉新版本并打印回退命令。迁移约定只做向后兼容的改动（加表、加列），删列放到下一个主版本。
- **部署验证**：`verify.sh` 只依赖 bash、docker、curl，客户现场和 CI 共用：健康检查和版本、经 web 打开页面和接口、超级管理员登录、“部署验证”知识库里的文档能入库和检索、问答可用、没有授权的员工账号选不到这个库且回答不引用它。CI 的 `deploy.yml` 在 `deploy/**`、迁移脚本改动和打 tag 时运行，用本地确定性模型跑三个场景：全新安装（有已发布版本时改为从最近的 Release 升级）、停服务备份 → 删卷 → 恢复、升级到一个带必然失败迁移的版本后按提示回退；打 tag 时通过后发布 Release。不加进分支保护的必选检查。
- **运维手册**：`deploy/README.md`，写给客户运维；根目录 README 只留开发内容并链接过去。
- **加固**：容器日志按大小轮转（每个服务 5 × 20 MB），三个服务 `restart: unless-stopped`，web 加健康检查；Compose 增加 `MODEL_BASE_URL`、本地模型开关和 `APP_PORT`。
- **另开的 Issue**：管理端窄屏适配另开 #130；Spring AI 升级（#131）经人答复“版本升级暂不考虑”，关闭。
