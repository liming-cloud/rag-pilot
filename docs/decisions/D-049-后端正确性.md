# D-049 后端正确性：资源授权在应用层、会话乐观锁、并发写入返回 409、模型调用不占事务、停机等后台任务（2026-11-03）

后端代码评审（#135、#136）经人答复：新建里程碑“1.0 收尾：后端代码质量”，拆成正确性与权限（#135）、结构整理（#136）两个 Issue。#135 的做法：

- **资源授权在应用层判定**：文档的上传、替换、改有效期、删除和管理端的调试检索，由应用服务带上操作人自己调 `getManageable`，不再依赖 Controller 先检查；删掉只按租户取库、不看操作人的 `KnowledgeBaseService.get`。权限语义不变（人答复同意）。检索时的授权过滤仍只在 `ChunkSearchMapper` 一处（D-041）。
- **会话并发用乐观锁**（人答复选乐观锁）：`conversation` 加 `version` 和 `last_turn_id` 两列（兼容的加列迁移，符合 D-048）。“只能重新生成或修改最后一轮”、新的一轮接在哪一轮之后，由 `Conversation` 聚合根据主线末尾判断，仓储不再判断；保存时版本已变就作废这次修改，提问返回 `ANSWERING_CONFLICT`（409），员工刷新后重试，回答记录随同一事务回滚。后台生成标题撞上时重新读一次再试，最多 3 次。主线改为从最后一轮沿 `parent_turn_id` 往回找，不再按轮次 id 排序：id 在开始生成时分配，先开始、后结束的一轮会排错。回答记录和会话在同一个事务里改两个聚合，是有意的例外：会话没接上时，回答记录也不该留下。
- **并发写入冲突返回 409**：知识库、角色（新建和改名）、账号、模型服务商的名称，以及同一个库里的同一份文件，先查重之后仍由数据库的唯一约束兜底，`DuplicateKeyException` 在应用服务里转成本模块的 `CONFLICT`，沿用 `AccountImportService` 的做法。
- **调用模型不占数据库事务**：模型管理的连通测试和读模型列表在事务外调用，测通后才开短事务写库；知识缺口、运营概览的归类和检索时给问题向量化不再开事务。这几处的多次读取本来就不要求同一快照。
- **停机等后台任务**：流式回答、会话轮次保存、标题生成、检索规划和低分改写不再各自 `static` 建线程池，统一用 Spring 管理的 `applicationTaskExecutor`（虚拟线程）。停机时最多等 30 秒（人答复，`spring.task.execution.shutdown`）；这个 bean 在 rag-app 里声明并依赖数据源，保证先等任务做完、再关连接池。Compose 的 `stop_grace_period` 设为 75 秒（Docker 默认只等 10 秒），留出 Web 优雅停机和后台任务各 30 秒。入库的 `IngestionWorker` 仍用自己的定长线程池限制并发，未完成的文档在下次启动时重新排队（文档表的“解析中”就是任务记录），不需要等。（#197 起改为 Spring 管理的 `ingestionTaskExecutor`，同样依赖数据源，停机时最多等 10 秒，75 秒仍够用。）
