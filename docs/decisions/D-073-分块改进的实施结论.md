# D-073 分块改进的实施结论：表格按行组切、每块带表头，升级后自动重新分块、旧分块正文留档（2026-11-18，#225）

按 D-069、D-070 实施“分块改进”时定下的做法，以及开工后人的答复（2026-11-18）。

## 分块规则（第 2 版，`TextChunker.VERSION = 2`）

- **表格**：Word、Excel、pptx 的表格由读取器单独成段，先写一行 `【表头】列1 | 列2 | …`，再每行一条“列名：值；列名：值”（原有写法）。分块时以 `【表头】` 开头的段落是表格：放得下就和前后正文一起装箱；放不下就按整行装成行组，每块以表头行开头、位置是所在章节，行不被切开，行组之间不重叠（每行本身带着列名）。
- **长段落**：先按行切，再按句子、按字符切（原来直接按句子切，“；”分隔的表格行会被切成单格）。
- **重叠**：仍取上一块末尾约 overlap 个 token，但其中有换行或句末标点时从下一行、下一句开始，不从半句开始。
- **章节**：分块的位置（文件名 > 标题 > …）仍随正文一起向量化，表格块因此也带着章节。
- 不做：语义分块、调用模型分块、PDF 表格识别（D-069）；用户自己写在 Markdown / 文本里的表格不识别。

## 分块参数

- 新配置 `rag.knowledge.chunking.max-tokens` / `overlap-tokens`（环境变量 `RAG_CHUNK_MAX_TOKENS`、`RAG_CHUNK_OVERLAP_TOKENS`），只影响之后入库的资料；`eval`、`eval-public` 工作流加输入 `chunk_max_tokens`，重叠按 16%（原来的 80 / 500）换算：300 / 48、500 / 80、800 / 128。
- 选定 **500 / 80**（默认值不变）：唯一只在一个评测集上不达标的一档；CRUD-RAG 拒答 -2.0 个百分点由人接受（2026-11-19）。

## 升级后自动重新分块

- 文档表加 `chunking_version`（升级前的都是 1）；写分块时记下当前版本。后台 `Rechunker` 每 10 分钟检查一次，在入库线程池里一次只做一份：读原文件 → 分块 → 向量化（事务外，被限流时按 #226 退避），再在一个事务里把旧分块正文留档、删掉旧分块、写入新分块、更新块数和版本、重算体检信号。替换之前旧分块照常参与检索。
- **可中断续做**：进度就是每份文档的版本；模型暂时不可用时这一轮停下，10 分钟后接着做；停机后重启接着做。处理期间文档被删除、修改有效期或被新版本替换（乐观锁不过）时这份不写回，下一轮再看；原文件读不出来或意外出错时保留旧分块，本次运行期间不再重试，重启后再试。
- **历史引用不失效**（人定，2026-11-18：改动范围小、影响面小、性能高的方案）：分块 id 会全部变化，而会话里的引用原文按分块 id 回查。重新分块前把旧分块的正文（不含向量）写进 `chunk_archive`，`accessibleContents` 查不到现行分块时查这里，授权过滤与现行分块相同（同一段 SQL），文档删除时一起删除。比较过的其他做法：保留旧分块行并标记退役（要改全部检索 SQL 和向量索引）、把旧 id 映射到新分块（摘录与当时回答依据的文字不一致）、接受摘录变空（不满足验收）。
- **标准题**（#224）存的是文档，重新分块不改文档 id，不受影响。
- CI 部署场景：在上一版本里上传一份资料，升级后等它被重新分块、旧分块已留档。
